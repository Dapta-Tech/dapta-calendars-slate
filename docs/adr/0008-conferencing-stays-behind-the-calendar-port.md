# Conferencing stays behind the calendar port; the vendor name arrives at runtime

R15 forbids naming a calendar vendor anywhere in this repo. The conferencing feature strains that rule in a way the rest of the calendar seam does not, because conferencing is the one part of it the *host* has to see and choose. A host picking how their invitees will meet them reasonably wants to know which platform they are picking, and "Automatic meeting link" answers that question with a shrug.

ADR 0001 set the precedent for relaxing this: it carved CRM integrations out of R15 and named HubSpot in-repo, on the grounds that a CRM integration is worthless if you cannot say which CRM it is. The same argument transfers to conferencing almost word for word, and we still refused it. The difference is which seam the feature rides. A CRM is its own package and its own port, added by this effort; conferencing rides the *calendar* port — the exact seam R15 exists to protect, the one whose adapter is a private overlay. Naming a vendor in `calendar-effects.ts` or in the shared i18n catalog puts the name on the public path itself, not beside it, and the current `location === 'google_meet'` literal is precisely the leak that proves how easily it happens.

So the code stays generic and the *label* is injected: the port may report a display name for the conferencing it provides, the private overlay supplies it, and the UI renders it when present. The repo names nobody; the running product names the platform the host actually connected.

Consequence: a bare fork with no calendar provider shows only the generic wording, which is correct — it has no conferencing to name. Anything vendor-specific about conferencing beyond the label (per-platform options, a platform picker independent of the connected calendar) is out of reach by construction, and would need this ADR revisited rather than a quiet exception. The trade is a slightly vaguer default UI in exchange for a seam that cannot leak a vendor name into the public tree.
