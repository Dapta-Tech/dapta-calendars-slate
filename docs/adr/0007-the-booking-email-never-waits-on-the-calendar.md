# The booking email never waits on the calendar

Every booking email is enqueued with its content already resolved: the outbox row snapshots the fully-rendered `BookingNotification` at enqueue time, deliberately, so that a later template edit cannot rewrite mail that is already queued. The conferencing link breaks that model, because it does not exist yet at enqueue time. It is produced by the *calendar* write-out — a different outbox row, drained later, by a worker that may retry for minutes. A confirmation email built from the enqueue-time snapshot can only ever say "Where: Automatic meeting link" with no link in it.

The obvious repair is to chain: hold the confirmation back and let the calendar job enqueue it once the link exists. We rejected it. Chaining makes the invitee's confirmation conditional on a third-party calendar API succeeding, and the failure it produces is the worst one available — a booking that is genuinely confirmed, holds a slot, and blocks the host's calendar, while the invitee is told nothing at all. Dead-lettered calendar rows are not hypothetical here: the pilot environments carry static dead-lettered rows today.

So the link is the one variable resolved at **delivery** time, read fresh from `booking_reference`, while everything else stays snapshotted. That alone leaves a race the invitee would lose often, so a conferencing booking's email row is also scheduled slightly late, and if the link is still missing when it comes due, the row retries on the normal backoff a small number of times before sending anyway. The wait is bounded and it always ends in a sent email.

Consequence: the ordering guarantee runs one way only. A calendar failure can cost the invitee the link in their email — never the email, and never the booking. The link is still reachable on the manage page, which reads the same row and therefore self-heals the moment the write-out succeeds. The inverse coupling, where mail waits on a vendor, is ruled out permanently: any future value that originates in an external system and belongs in an email inherits this pattern — resolved at delivery, bounded wait, degrade to absent.
