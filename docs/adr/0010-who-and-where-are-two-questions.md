# Who is calling and where they act are two questions

Until now one answer covered both. The auth provider validated the session token and resolved an account and a member from it, and that account was the only one the person could ever act in. The data model already allowed more: `member` is unique per `(account_id, external_id)`, and inviting someone writes an `invited` row into the inviting account. Nothing read that back. An invited teammate signed in, landed in their own account (or got a new empty one), and the invitation led nowhere.

The provider still answers the first question, unchanged: who this is, from the token it validated, and their home account. The second question gets its own input. A dashboard request may name another account in `x-dcal-workspace`, and that name is only a request: `AuthService` re-derives the membership from the database on every call, from the identity the provider proved. A name the person holds no membership in, or a disabled one, is a 403 `WORKSPACE_FORBIDDEN`, never a quiet fall back to the home account: a fallback would land writes in a tenant the person did not believe they were in. The web keeps the choice in an httpOnly cookie (`__Host-` in production), drops it when the API refuses it or the session ends, and re-renders a tab that comes back into view after another tab changed it.

Only memberships this app granted count. A member row the provider created because a token named that account stays reachable only through such a token: the identity service is not obliged to tell this app when it removes someone, so honoring that row from another account's token would outlive the removal, on the web and through the MCP door alike. Rows that came from an invitation carry `member.invited_at` (an additive column; pending invitations are backfilled), and those are the only ones a header can reach. A person matches them by their subject, or, while the invitation is not yet bound to anyone, by the address the session's token vouches for (never one it marks unverified, never a stored address that may be stale).

Accepting is a deliberate act: a POST the person makes, from the workspace switcher or the Join button on the invitation page. Opening the email's link, or naming a pending workspace in the header (403 `INVITATION_PENDING`), accepts nothing, so nobody can join a workspace on someone's behalf by sending them a link. Accepting turns the row active with the invited role and binds it to the person's subject, so it follows them and the MCP door (which finds a person's accounts by subject) sees it. A disabled member stays disabled.

What does not change is the point. No header, or the home account named, is exactly the provider's answer, so every caller that never sends it (API keys, the MCP door, public pages, webhooks, any fork) behaves as before, and connecting an app through OAuth consent always speaks for the home account. Nothing is emailed on deploy.

This is the shape dForms reached first, with the identity service's own workspaces as the source of truth behind it. Projecting those workspaces here is a later step and does not change this contract: the header still names a local account, and membership is still re-derived per request.
