The calendar event's own title and description, as templates a host writes per event type: `Reunión Felipe - {{name}}` as the title, the answers in the description (`{{#if form.company}}Company: {{form.company}}{{/if}}`). Same language and variables as email (`@slate/engine`), rendered for the host's calendar: in the host's language, times in the host's zone (`*_attendee` for the invitee's).

`event_type` gains `calendar_title_template` and `calendar_description_template`; `booking` gains `calendar_description` and `seated` (migrations `postgres/0029` and `sqlite/0028`, nullable, no default; `lock_timeout` bounds the lock on `booking`; the one backfill sets `seated` on every booking that already holds more than one attendee, since a row cannot tell a seat-taker from a guest and over-marking is the safe side). NULL is "no template": the title stays the event's name and the event has no description, exactly as before. `POST` and `PATCH /v1/event-types` take `calendarTitleTemplate` and `calendarDescriptionTemplate` (null or blank clears one) and `GET` returns them.

The data layer renders them when a booking is placed and again when it moves, on every path that does either (personal, team, the v1 move and the v2 move's new booking), and stores the result in `booking.title` and `booking.calendar_description`, only onto the time it rendered for (a move that lands meanwhile writes its own). Everything that already read the title (the calendar write, both .ics files, `{{event_title}}` in email, the confirmation, the manage page, the CRM) reads the rendered one. The description reaches the organizer's event and its move (`UpdateEventInput.description`, sent only when the booking's body came from a template, so an event without one is never touched), each co-host's copy above its join line, the emailed invite and the confirmation's "Add to calendar" file as `DESCRIPTION`, and the booking answer as `calendarDescription`. A title that renders empty falls back to the event's name. A move with no title template keeps the title the booking has; a description the template no longer writes is emptied (`''`) and the move clears it on the calendar, so no stale time stays in the event. A render never fails a booking; a failure is logged.

A calendar event is seen by its guests, so these templates are checked for the invitee: the manage links, the meeting link, `{{guests}}` and `{{booking_link}}` (now email-only) are refused. On an event with seats, everyone who takes a seat is a guest on one event, so one invitee's data (name, email, phone, time zone, `*_attendee` times and every answer, marked `perInvitee` in the catalog) is refused too, also when a save turns seats on, and renders empty if a stored template names it. A booking someone took a seat on is marked (`booking.seated`) and keeps rendering that way after the event type's seats are turned off. Taking a seat renders the slot's text again as shared, so the person joining never reads the first booker's title or description from before the seats existed; without a template a shared slot goes back to the event's name and no description, and the seat-taker's answer carries only that text. Values lose `<` and `>` on top of the usual cleaning. The 400 (`INVALID_TEMPLATE`) names the field (`calendarTitleTemplate`, `calendarDescriptionTemplate`) in the host's language. The new issue code is `per_invitee`.

The engine now treats U+2028 and U+2029 as line breaks (folded in a title, a newline in a body) and reads at most 50 items of a list answer, each cut to 2000 characters, before formatting or comparing it; both .ics escapers write those separators as `\n`. The time and duration formatters and the answers map move into the engine (`formatTemplateTime`, `formatTemplateDuration`, `templateFormValues`); `@slate/notifications` keeps `formatWhen`, `formatDuration` and `formVars` as the same functions. The web .ics escaper folds a lone CR.

A calendar backend receives `description` as plain text on create and, when set, on update: write it as text, not HTML; on a PATCH, absent leaves the body as it is and an empty string clears it (see SELF-HOSTING.md, "The event body").
