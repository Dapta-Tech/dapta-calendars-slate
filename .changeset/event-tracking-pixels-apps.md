Tracking and pixels per event type, off unless the deployment allows the workspace. The tags run the host's own JavaScript (a GTM container can carry any script) on the same origin as the dashboard and its session, so `EVENT_TRACKING_ACCOUNTS` names the workspaces that may use them (account short codes or vanity slugs, or `*`); unset, nobody can, and every public read drops stored ids at once when a workspace leaves the list. Only owners and admins can set or change the ids; a member's save that sends them back unchanged still passes. `/v1/me` answers `eventTrackingEnabled`.

The event type editor shows a "Tracking and pixels" section to owners and admins of an allowed workspace, one field per tag with a line saying when it fires. On the event's booking page (personal, team and one-off link pages, embedded or not; never the dashboard, the studio preview, the manage page or the profile pages) each tag loads only when its id is set, from module code with the id as data, so nothing is interpolated into an inline script: GTM's container; Meta Pixel with one PageView (history changes are not pages); the host's PostHog, pageview only (no autocapture, replay, heatmaps or surveys, which would record what an invitee types), as its own named instance on the loader dCal's analytics already uses, with the library always from the vendor's CDN; HubSpot's tracking code. When someone books, Meta gets `Schedule` and GTM `booking_scheduled`, once per booking, before any redirect after booking, which then waits 300 ms so the requests are not cancelled. These carry nothing about the invitee; what a vendor collects on its own (Meta's automatic advanced matching, HubSpot's collected forms) follows the host's settings in that vendor. From a profile or team page, an event that has tags opens as a full page load, so its tags live only in its own document. See `event-tracking-pixels.md` for the data side.
